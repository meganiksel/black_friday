## Задание 7. Схемы коллекций и шард-ключи

### Коллекция `orders`

**Назначение:** заказы, история по пользователю, статус, геозона.

**Пример документа:**

| Поле | Тип | Комментарий |
|------|-----|-------------|
| `_id` | ObjectId | идентификатор заказа |
| `customer_id` | string / ObjectId | клиент |
| `created_at` | date | время оформления |
| `items` | array | `{ product_id, price, qty }` |
| `status` | string | lifecycle заказа |
| `total` | decimal | сумма |
| `geo_zone` | string | геозона |

**Кандидаты shard key:** `customer_id` (низкая кардинальность при крупных B2C — риск горячих шардов), `_id` (хорошее распределение, но плохая локальность для запросов «все заказы пользователя»), составной **`{ customer_id: 1, _id: 1 }`**.

**Стратегия:** **compound hashed** или **range** по `customer_id` + суффикс, если нужна локальность запросов по пользователю без scatter-gather. Для равномерности при огромном числе пользователей часто берут **`{ _id: "hashed" }`** для записи и отдельные индексы под запросы по `customer_id` (с пониманием multi-shard queries).

**Пример включения шардирования:**

```javascript
sh.shardCollection("shop.orders", { customer_id: "hashed" })
// либо после создания индекса:
// db.orders.createIndex({ customer_id: 1, _id: 1 })
// sh.shardCollection("shop.orders", { customer_id: 1, _id: 1 })
```

### Коллекция `products`

**Назначение:** каталог, остатки по геозонам, фильтры по цене/категории.

**Пример полей:** `_id`, `name`, `category`, `price`, `stock_by_zone` (вложенный объект или массив), атрибуты.

**Риск:** популярные категории (например «Электроника») дают перекос по shard key только из `category`.

**Стратегия:** shard key с **высокой кардинальностью** и **равномерным распределением**, например **`{ _id: "hashed" }`** или **`{ sku: "hashed" }`**, а запросы по категории обслуживать через индекс и допускать multi-shard aggregation при необходимости.

```javascript
sh.shardCollection("shop.products", { _id: "hashed" })
```

### Коллекция `carts`

**Назначение:** активные корзины, TTL, слияние гостевой и пользовательской.

**Ключевые поля:** `_id`, `user_id`, `session_id`, `items`, `status`, `created_at`, `updated_at`, `expires_at` (TTL index).

**Стратегия:** шардирование по **`user_id`** или **`session_id`** (в зависимости от доминирующего доступа) с **дополнением полем с высокой кардинальностью**, чтобы избежать hot shard у одного «суперпользователя», например **`{ user_id: 1, _id: 1 }`** или hashed по `user_id`, если допустимо.

```javascript
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })
sh.shardCollection("shop.carts", { user_id: "hashed" })
```

## Задание 8. «Горячие» шарды: метрики и перераспределение

### Метрики

| Метрика | Зачем |
|--------|--------|
| Операции чтения/записи по шарду (`mongos` / `FTDC`, Prometheus exporter) | выявить перегруженный shard |
| Размер данных и число чанков на шард (`sh.status()`, `db.getSiblingDB("config").chunks`) | дисбаланс данных |
| CPU / IOPS / latency на узлах shard | узкое место инфраструктуры |
| Длина очереди balancer, скорость миграций | фоновые переносы в пике нагрузки |
| Запросы с высоким `docsExamined` / scatter-gather | плохой выбор shard key или индексов |

### Меры

- **Balancer / moveChunk** (или автоматический балансировщик в новых версиях) для перераспределения чанков.
- **Изменение shard key** (редко, дорого) или **репликация в новую коллекцию** с новым ключом.
- **Сегментация по категориям** в приложении (отдельные коллекции/кластеры) для изоляции горячих категорий.
- **Кеш (Redis)** и **снижение частоты тяжёлых запросов** к «горячим» данным.

Пример просмотра чанков:

```javascript
use config
db.chunks.find({ ns: "shop.products" }).count()
```

## Задание 9. Чтение с primary и secondary

Допустимая задержка репликации (**replication lag**) зависит от SLA: для остатков товара — секунды недопустимы при риске оверселлинга; для рекомендаций — допустимы единицы секунд.

| Операция / коллекция | Primary / Secondary | Допустимый lag | Обоснование |
|---------------------|---------------------|----------------|-------------|
| Создание заказа + списание остатков (`products`, `orders` write) | **primary** | — | нужна линейная запись и согласованность транзакции |
| Чтение остатка перед оплатой (`products`) | **primary** или **secondary** с `readConcern: majority` / проверка версии | **&lt; 100–300 ms** в зависимости от SLA | риск продать отсутствующий товар при stale read на secondary |
| Каталог / фильтр по категории (`products`, read-heavy) | **secondary** с `secondaryPreferred` | **1–5 s** типично | допустимо устаревание цены/остатка для витрины при явном дисклеймере |
| История заказов пользователя (`orders`) | **secondary** | **до нескольких секунд** | реже критично, чем оплата |
| Активная корзина (`carts`) | **primary** для merge/update | — | гонки при логине/слиянии гостевой корзины |
| Просмотр корзины после недавнего обновления | **primary** или causal | **минимальный** | согласованность с только что добавленными позициями |

## Задание 10. Cassandra

### 10.1 Критичные данные

| Данные | Cassandra уместна | Комментарий |
|--------|-------------------|-------------|
| Поток заказов, события статусов | Да | высокая запись, горизонтальное масштабирование |
| Каталог и остатки (strong consistency) | Обычно **нет** как единственный источник без оговорок | CAS/LWT ограничены; часто остаётся Mongo/SQL + кеш |
| Корзины / сессии | Частично | TTL-friendly, но сложные обновления проще в Mongo/Redis |
| История заказов для аналитики | Да | широкие строки, time-series по партициям |

### 10.2 Модель и ключи (пример)

**Заказы по пользователю и времени**

- **Partition key:** `(customer_id)` — локальность по клиенту.
- **Clustering key:** `(order_time DESC, order_id)` — сортировка истории.

```sql
CREATE TABLE orders_by_customer (
  customer_id uuid,
  order_time timestamp,
  order_id uuid,
  status text,
  total decimal,
  PRIMARY KEY ((customer_id), order_time, order_id)
) WITH CLUSTERING ORDER BY (order_time DESC);
```

Равномерность: партиции по активным пользователям; «звёздный» клиент даёт hot partition — смягчается rate limiting и отдельная очередь.

**События статусов (append-only)**

- **Partition key:** `(order_id)` или `(shard_of_order_id)` — равномерно по заказам.

### 10.3 Целостность: Hinted Handoff, Read Repair, Anti-Entropy

| Механизм | Смысл | Где уместнее |
|----------|--------|----------------|
| **Hinted Handoff** | временная буферизация записи при недоступной реплике | высокая доступность записи событий заказа |
| **Read Repair** | починка устаревших реплик при чтении | чтение истории заказов с `ONE`/`LOCAL_QUORUM` |
| **Anti-entropy repair** | фоновое согласование (nodetool repair) | регулярное обслуживание для слабо читаемых партиций |

Для **финансово значимых** сущностей комбинируется **QUORUM/LOCAL_QUORUM** + мониторинг repair, для **логов/аналитики** допускается **ONE** на чтение с фоновым repair.
